If this change is not implemented, customers will continue to follow the old renewal cycle, resulting in incorrect KYC renewals and compliance issues.

⸻

Scope

* Update 318 High and Medium Risk customer records.
* Update KYC Expiry Date using the business-provided data.
* Target databases:
    * PostgreSQL
    * Oracle
    * RM Database

⸻

Implementation Plan

1. Take a backup of the affected tables in PostgreSQL, Oracle, and RM databases.
2. Verify the business-provided file containing:
    * CRMS Case ID
    * Existing KYC Expiry Date
    * New KYC Expiry Date
3. Validate the total record count (318 records).
4. Execute the data patch using the following logic:
    * If Case Status = C, update the KYC Expiry Date in all databases.
    * Else, if Case Status ≠ C and KYC Reason = Maintenance, update the KYC Expiry Date in all databases.
    * Otherwise, do not update the record and prepare a list of skipped records.
5. Update PostgreSQL database.
6. Update Oracle database.
7. Update RM database.
8. Validate that all successful records have been updated.
9. Share the validation report with the business team for confirmation.

⸻

Business Impact

* Existing High and Medium risk customer records will follow the new renewal cycle.
* KYC renewal dates will be corrected.
* Business users will see the updated expiry dates after the patch.
* No impact is expected on normal business operations during the maintenance window.

⸻

Technical Impact

* Data will be updated in PostgreSQL, Oracle, and RM databases.
* Approximately 318 records will be modified.
* Auto synchronization between databases is not available; therefore, each database must be updated separately.
* No application code changes are involved.

⸻

Backout Plan

If any issue occurs during implementation:

1. Stop further execution immediately.
2. Restore the affected records from the database backup.
3. Verify that the original KYC Expiry Dates are restored.
4. Inform the business and stakeholders.

2. Extract KYC Expiry Date from PostgreSQL, Oracle, and RM databases.
3. Compare the updated values with the business-provided file.
4. Verify that skipped records match the expected conditions.
5. Obtain business confirmation after validation.

⸻

Rollback Criteria

Rollback will be initiated if:

* Incorrect KYC Expiry Dates are updated.
* Record count does not match the expected 318 records.

* Business validation fails after implementation.

public class ArabicToHtmlEntity {

    public static String encodeToHtmlEntities(String input) {
        StringBuilder result = new StringBuilder();

        for (char ch : input.toCharArray()) {
            // Preserve spaces, tabs, and new lines
            if (ch == ' ' || ch == '\n' || ch == '\r' || ch == '\t') {
                result.append(ch);
            } else {
                result.append("&#").append((int) ch).append(";");
            }
        }

        return result.toString();
    }

    }

Process Overview

The Monthly Refund Commission file uses a sequence number to maintain the upload order. During each upload, the HUB validates the sequence number.

* If the uploaded file contains the expected sequence number, the file is accepted and processed successfully.
* If the sequence number does not match the expected sequence, the HUB rejects the file, and the upload fails.

Therefore, the sequence number must always follow the expected order without any gaps.

Root Cause Analysis

The last successful upload in the HUB was completed in December 2025 (evidence attached).

The January 2026 monthly file was not uploaded. Since no file was processed in January, the expected sequence number in the HUB remained at 811 and did not increment.

However, the subsequent monthly files were uploaded using the next sequence numbers instead of the sequence number that the HUB was still expecting. As a result, the HUB rejected these uploads because of the sequence number mismatch.

If the January 2026 upload issue had been identified and reported at that time, the sequence could have been corrected immediately. However, the issue was not flagged by the Operations team, and the same incorrect sequence number continued to be used in the following monthly uploads.

* The last successful HUB upload was completed in December 2025.
* The January 2026 upload was not performed.

* There is no technical issue with the HUB upload process or the OMS application.

Based on our investigation, the issue is not caused by an application or technical defect. The root cause is a process/control gap, where the January 2026 upload was missed and the sequence number mismatch was not identified before subsequent monthly uploads were performed.

“From an IT perspective, we can certainly enhance the system by adding automated reconciliation or exception reporting. However, ownership of the operational control is a business decision and should be agreed between the business, Operations, Risk, and Compliance teams.”
